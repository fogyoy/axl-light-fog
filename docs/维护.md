# 维护与验证

## 命令

- `npm run verify`：运行项目的静态检查、构建和自动化回归验证。
- `npm run test:obsidian -- --vault-path <测试库>`：在指定的 Obsidian 测试 vault 执行实机验收。该 vault 必须与个人日常 vault 分开。
- `npm run release -- --version <版本>`：按指定版本准备发行产物。版本号需与插件清单及发行标签一致。
- `npm run install:local -- --vault-path <库>`：备份并安装到明确指定的笔记库。日常笔记库使用已发布且验收通过的安装包，可通过 `--from <解压后的插件目录>` 指定；实机测试仍只在独立测试库运行。
- `npm run rollback:local -- --backup <备份>`：从指定备份恢复本地插件安装。

## 验收边界

正式实机测试始终使用独立测试 vault，避免测试数据与个人标注混杂。普通 CI 在 GitHub 托管 runner 上执行 `npm ci` 和 `npm run verify`，不访问、不连接任何维护者本机或本机 vault。

macOS 是当前优先验收平台；Windows 与 Linux 尚未验证。测试记录应注明 Obsidian 版本、操作系统、测试 vault 是否为隔离库，以及实际覆盖的操作。

## 准备独立验收库

先运行 `npm run verify`，再运行 `npm run test:setup`。在 Obsidian 中将命令输出的文件夹打开为笔记库，确认社区插件可以运行。以后测试使用这个目录作为 `--vault-path`，不要传入日常笔记库。测试入口先验证标记、CLI 实际路径和已安装文件校验值，再创建合成数据。

开发使用 Node.js 26.13.0、Python 3 和已开启命令行界面的 Obsidian 1.15.1。维护脚本还需要已登录维护者账号的 GitHub CLI。

实机测试会将专用测试窗口切到前台，以便 Obsidian 渲染阅读视图；运行时保持屏幕解锁。CLI 中的长中文代码和结果使用 ASCII 传输编码，避免文本分块破坏验收记录中的中文。

发布工具会检查稳定 main 的 CI 与同提交实机凭证，重新生成安装包，再创建 GitHub Release。重复发布会校验已有资产，内容不同则停止，不强制替换。

## 演练旧版身份迁移和回退

运行 `npm run test:installation -- --vault-path <测试库> --legacy-package <旧程序目录>`。旧程序目录包含原 `axl-light-zh` 的程序清单与样式，可从自己的停用安装副本准备，不能加入公开仓库。测试会使用合成设置和标注验证迁移、回退以及再次迁移，结束时恢复测试库原插件状态。演练还会检查回退后保留迁移之后新增的标注。

发布要求 `.local/evidence/obsidian.json` 和 `.local/evidence/installation.json` 都对应当前提交。安装工具只搬运指定安装包和必要的身份设置，不改写旁注；首次迁移回退时，新创建的设置副本另存于私有备份中，再撤销它，防止下次迁移误用过期副本。

## 匿名合并维护 PR

PR 通过必要检查后，运行 `npm run merge -- --pr <编号>`。工具从当前 GitHub 账号计算匿名邮箱，并显式传给合并接口。仅配置本地 Git 邮箱无法约束 GitHub 服务端生成的合并提交，因此日常维护统一使用这个入口。

首次使用前，在 GitHub 的「Settings → Emails」开启「Keep my email addresses private」。若接口拒绝匿名邮箱，工具停止合并并提示设置位置，不会回退为账号默认邮箱。合并同时锁定已检查的 PR 提交，防止检查结束后新增的代码被直接合入。

Obsidian CLI 的库选择参数必须放在命令前。维护工具使用 `obsidian vault=<库名> eval ...`，每次写入前还会核对实际路径。不要调整为命令后的参数位置。
